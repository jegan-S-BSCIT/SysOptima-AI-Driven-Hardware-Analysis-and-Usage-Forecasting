### Expected Examiner Questions & Answers

**Q1: "Why do you need real-time monitoring?"**
> Real-time data shows how the system behaves under actual workload. Static benchmarks alone are insufficient. The diagnostics engine needs live metrics to understand current behavior and make recommendations.

**Q2: "Why threading?"**
> We can't block the UI while collecting metrics. A background thread collects every second while the main thread keeps the UI responsive and interactive.

**Q3: "How do you ensure thread safety?"**
> We use `threading.Lock` mutex to protect the shared data buffer. Only one thread can access the buffer at a time, preventing race conditions and data corruption.

**Q4: "What if GPU is unavailable?"**
> We check for GPU at startup using GPUtil and nvidia-smi. If neither is available, the system gracefully continues, displaying 0% or "N/A" instead of crashing. This is proper error handling.

**Q5: "How much overhead does this add?"**
> The collection thread uses ~0.2% CPU (mostly sleeping). Memory usage is fixed at ~13 MB total (3 MB for engine buffer, 10 MB for Matplotlib charts). Negligible for a system analysis tool.

**Q6: "How would you extend this?"**
> The modular design makes extending easy. We could add: network I/O metrics, temperature monitoring, process breakdowns, data persistence, or alert notifications. The engine/UI separation keeps changes isolated.

**Q7: "Why a 30-second window?"**
> 30 seconds provides enough history to see trends while keeping memory usage bounded and relevant to real-time analysis. Configurable if needed.

**Q8: "What about the diagnostic thresholds?"**
> Thresholds (CPU>85%, RAM>80%, Disk>50 MB/s) are based on industry standards and tunable. They're intentionally simple—rule-based, not ML—for clarity and explainability.
